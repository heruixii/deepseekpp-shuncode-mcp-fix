## 1. 已确认：只读工具自动重试与单次授权冲突

- 11:42:46.280：read_image，调用 ID `turn:7:xml:0`，返回 `mcp_http_error` / HTTP 503，摘要为 MCP 服务初始化失败，retryable=true。
- 11:42:47.316：同 ID、同参数重试，返回 `tool_call_replayed`，提示调用已经 reserved 或 consumed，retryable=false。
- 源码：content 的 `i2` 在 `DPP_WEB_SAFE_RETRY_3` 判为可重试后再次调用 `o2(i,r)`，未改变调用身份。后台 `ya` 通过 `ca` 决定授权是否可重试；当前 `ca` 只允许 local:web:web_fetch 的 fetch_permission_denied，同一次 MCP read_image 不在允许范围内。

结论：第一条是真实 MCP HTTP/初始化失败；第二条是扩展重试策略和授权状态机不一致造成的二次失败，不是 MCP 又断了一次。防重放拒绝本身符合当前安全设计。

建议 P1：统一传输失败阶段、结果确定性、重试资格和授权决策。不得仅以 retryable=true 或工具名称含 read 判断可复用授权；不得关闭防重放。只有能证明未执行或明确允许幂等只读重试时，才按受限规则重试；副作用调用结果不明时禁止自动重放。

## 2. 已确认：搜索遇到 Windows 特殊路径

11:05:32.389 search_files：`mcp_tool_result_error`，IO_ERROR，`rg: .\Athena计划\NUL: 函数不正确。 (os error 1)`，retryable=false。

这是文件搜索/文件系统错误，不是工具列表丢失，也不是 DeepSeek generation_err。建议 P2：先只读核实 NUL 条目的实际类型、创建来源及遍历规则，按边界跳过不支持条目并明确报告部分失败；本次未删除或改名任何文件。

## 3. 已确认：重开后工具正常注入，但上游连续 generation_err

网页桥时间线：

- 11:43:59.977 bridge_close；11:44:01.761 boot；11:44:02.769 bridge_open，随后工具数恢复为24。
- 11:45:31.997 completion assistant198：HTTP200，但 SSE finish_reason=generation_err；273字符原始提示扩展为35651字符；工具24个，recoveryMode=None。
- 第一次失败于11:45:31.996为 assistant198 登记 compact 恢复。
- 11:45:43.338 用户下一次请求走 editMessage；11:46:32.247 assistant200 再次 generation_err。232字符扩展为35610字符，recoveryMode=None。

源码确认：`ja` 从 parent_message_id 读取恢复关联；`DPP_RECOVERY_MODE_331020` 要求请求 parentMessageId 严格等于上一次失败的 assistantMessageId。此次 editMessage 请求没有符合该条件的 parent，故即使在 .47 的10分钟窗口内也不使用精简恢复。

另：恢复标记及失败计数存储在 main-world 的内存 Map，页面重建即重新初始化。关闭重开不会删除服务端同一会话历史，却会失去页面内存中的恢复状态。这是机制边界；不能把11:44重开后出现的11:45失败标记说成已被11:44重开清除。

建议 P0：覆盖 completion/editMessage 的实际失败分支身份关联；如持久化恢复状态，必须限定会话、失败分支、TTL、一次性消费并防止跨分支误用。精简恢复只减少新注入内容，不会自动压缩服务端旧历史，也不保证上游一定生成成功。

## 4. 长会话是风险线索，尚不是证实的根因

该会话保留99条用量记录。服务端累计 token 指标从 assistant2 的8675增长到 assistant194 的205833，assistant198/200 为216343。源码字段来源是 accumulatedTokenUsage。

**该指标不是已核实的单次输入上下文长度，更不能直接证明超过某个模型硬上限。** 约3.56万字符的新请求扩展内容、长工具任务历史以及服务端 generation_err 需要一起分析。此前同级大小请求也有成功记录，不能断言“只要提示太长就必然失败”。

建议 P1：增加真实请求/上下文预算诊断；用精简交接摘要在新会话做受控对照，而不是反复在同一失败分支点击重试。若新会话正常，能支持历史/分支相关性，但仍不是单变量根因证明。

## 5. 任务中断：持久化状态和执行时间线不一致，确切触发点尚未证实

当前任务 loop417c…：持久化 trace updatedAt=11:42:59.426，status=stopping，error=已停止，只包含8个完整步骤、totalTools=1。但同 loop 的其他日志继续记录11:43:43命令结果、11:43:51读图成功、11:43:56第11次工具决策，随后11:43:59网页桥关闭。

源码存在 pagehide 主动停止任务的处理，也存在停止时异步写 trace；本次证据不足以确定用户所说的那次中断是人工停止、页面生命周期事件、跨页面竞争、持久化丢失还是其他异常。不能把旧 trace 的11:42:59直接当作实际停止时刻，也不能把 read_image 的503说成整项任务当场停止：后面明确还有活动。

建议 P1：补齐 pagehide/用户停止/异常/导航的独立原因码、页面实例ID、单调事件序号、最后已确认工具结果及持久化确认；审计跨页面写入和停止后的在途操作收尾。恢复应先核实工作产物，不得依据陈旧 checkpoint 自动重放已执行命令。

## 结论与边界

.47 未解决所有上游生成错误。当前可证实的扩展缺口至少有：editMessage 恢复未命中、页面重建不保留恢复状态、MCP只读自动重试与授权消费冲突。任务 trace 与后续活动不一致需要继续定位，尚不能宣布其确切代码根因。

优先顺序：P0 失败分支恢复覆盖 → P1 安全重试与授权统一、checkpoint一致性及长会话预算 → P2 特殊路径搜索容错。此报告仅提出方案，未执行修复或部署。
